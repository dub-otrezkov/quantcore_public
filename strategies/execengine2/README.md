# execengine2

Новый движок добавлен рядом со старым `execengine`. Он не меняет старые точки
запуска: переход можно делать по одной стратегии после тестов на реальном runner.

**V2 пока не обеспечивает поведенческую совместимость с v1.** В
[аудите совместимости](PARITY_AUDIT.md) сохранены подтверждённые расхождения,
включая превышение целевого объёма и незавершённые клипы. До устранения блокеров
и проверки реального runner этот пакет не является готовой заменой v1.

## Устройство

`Engine` — тонкий вход для событий. Изменяемые данные разделены между пятью
частями:

```text
Engine
├── quotes  — цены пары и их возраст
├── trade   — одна текущая парная сделка
├── orders  — наши заявки и защита от повторных fill
├── hedges  — проверка market-заявок и отложенные хеджи
└── run     — ready, fixing, check_needed или stopped
```

Части не читают поля друг друга. Они возвращают обычные значения, а `Engine`
вызывает `Broker`, `Strategy`, `SendLimit` и `Updates`.

Все методы `Engine` вызываются из одной горутины цикла событий. Внутри движка
нет мьютексов и фоновых горутин. В `ModeMarket` две короткоживущие горутины
параллельно вызывают только `Broker.Place`; движок ждёт обе и затем учитывает
оба результата в цикле событий. Ошибка одной ноги не теряет результат второй.
Брокер и общий лимит сами отвечают за доступ из нескольких горутин.

## Основной поток

1. `OnBook` сохраняет bid/ask и меняет цену открытой limit-заявки.
2. `OnSignal` получает `Plan` от стратегии и создаёт заявки новой сделки.
3. `OnFill` учитывает fill один раз. Первый fill снимает вторую limit-заявку и
   отправляет market-хедж.
4. `OnTick` проверяет таймауты, market-заявки и работу после ошибок брокера,
   включая продолжение неизвестных отправок по исходному client ID.
5. `CheckPositions` возвращает движок в `ready`, только когда позиции равны и
   не осталось заявок или хеджей в работе.

Первый запрос статуса market-заявки выполняется через `MarketCheckAfter`.
Следующий интервал равен `MarketCheckEvery`, затем он удваивается до `RetryMax`
(не меньше `MarketCheckEvery`) отдельно для каждой заявки. Ошибка или
нетерминальный ответ сохраняет это расписание; терминальный статус или полный
fill снимает заявку с проверки. Пропущенные тики не вызывают серию догоняющих RPC.

Режимы исполнения: `ModeTwoLimits`, `ModeLimitA`, `ModeLimitB` и `ModeMarket`.

## Лимит отправки

`budget.Atomic` хранит неизменяемый `reserve` и ровно одно изменяемое поле:
`atomic.Int64 remaining`.

- `Take` одной CAS-операцией проверяет и сразу списывает попытки;
- обычная заявка не может взять `reserve`;
- обязательный хедж может взять запас и увести остаток ниже нуля;
- `SetIfLower` принимает от брокера только меньшее значение;
- `Reset` вызывается снаружи; готовый `Controller` делает это по таймеру.

В лимите нет `time.Time`, mutex, пары `Allow`/`Spend` и возврата попытки после
ошибки. Попытка отправки уже могла дойти до брокера, поэтому она считается
потраченной.

## Ошибка отправки

Broker должен вернуть:

- `NotPlaced(err)`, если заявка точно не создана;
- `OrderUnknown(clientID, err)`, если заявка могла быть создана.

Неизвестная market-заявка сохраняется вместе с исходным запросом и client ID.
`OnTick` через `PlacementResumer` сначала ищет её у брокера, затем при необходимости
продолжает идемпотентную отправку с тем же ID. `finambroker.Gateway` реализует этот
контракт; каждый повтор списывается как обязательное восстановление, а ожидание
останавливается через `ctx`. Один вызов восстановления делает не больше одной
отправки без внутренних пауз; следующую попытку назначает `OnTick`. Первая попытка
идёт через `RetryWait`, затем интервал для каждой неизвестной заявки удваивается
до `RetryMax` (не меньше `RetryWait`). Проверка позиций не сбрасывает эту задержку.
Нулевая или частичная позиция не снимает барьер
неучтённой заявки: она ещё может исполниться позже. Полный снимок позиции может
подтвердить уже учтённый хедж, исчезнувший из списка активных заявок. Для неизвестных
ног `ModeMarket` требуется ровно полная целевая пара относительно позиции до
начала сделки и отсутствие других незавершённых обязательств. Позиция в этой
ветке точная, а цена приближённая: заявка не регистрируется в `orders`, поэтому
поздний fill с реальным broker order ID отбрасывается и аменда цены не будет.
В учёте остаётся встречный тач на момент постановки, как у `acceptUntrackedMarket`.
Потребитель `Updates`, использующий среднюю цену для риск-предохранителей,
должен учитывать эту погрешность цены исполнения.

Шлюз хранит исходный запрос и ограничивает повторы ближайшей полуночью UTC или
Москвы; после этой границы или пересоздания шлюза доступен только поиск заявки.
Новый торговый день не продлевает окно повторной отправки старого ID.
После первого `AlreadyExists`, в том числе при исходной отправке, шлюз оставляет
для этого ID только поиск: повторная отправка уже бесполезна. Отсутствие заявки
в списке активных по-прежнему не доказывает, что она не исполнилась, поэтому
барьер сохраняется до подтверждения или вмешательства оператора.

После подтверждения движок проверяет фактическое исполнение и ставит хедж только
на недостающий объём. Ранее предварительно учтённый хедж повторно не зачисляется.
Пока исход неизвестен, движок не рассчитывает новый балансирующий объём по
сомнительной позиции. Уже записанные долги можно исполнять: это точно неотправленный
остаток либо подтверждённый недобор конкретной терминальной заявки.
`Stop` запрещает в том числе продолжение неизвестных отправок.

Без `PlacementResumer` или сохранённого client ID автоматическое продолжение
невозможно: неизвестная market-заявка остаётся под барьером. `OnTick` сообщает
причину через `Warnf` по тому же расписанию с ростом интервала; после `Stop`
эти предупреждения прекращаются. Неизвестные лимитные заявки используют прежнюю
проверку позиций.

Для явных отказов обязательного хеджа `RejectRetryLotStep > 0` включает уменьшение
размера попытки до одного лота. Принятые части накапливаются до исходного объёма;
недостающий остаток никогда не списывается. После отказа на минимальном размере
выполняются `HedgeTries` попыток остатка, затем он сохраняется как долг.
Повтор долга проходит через ту же лесенку; в очереди остаётся только ещё не
размещённый объём. Принятый или двусмысленный чанк вычитается из долга, поэтому
неизвестная заявка не блокирует другие долги и неотправленный остаток того же
хеджа. Например, после двусмысленных 4 лотов из 10 повторяются только оставшиеся
6; если позднее подтвердится недобор в исходных 4, он станет отдельным долгом.
При `RejectRetryLotStep == 0` действуют только обычные `HedgeTries`.

Лесенка в v2 применяется только к обязательным хеджам. Размер первого размещения
закрывающего клипа в `ModeTwoLimits`, `ModeLimitA` и `ModeLimitB` не уменьшается
после отказа, хотя v1 умеет повторить такое закрытие меньшим объёмом. Это осознанно
оставленное различие: настройка `RejectRetryLotStep` в v2 пока не даёт такого
поведения первому maker-размещению. В `ModeMarket` размер пары также не уменьшается,
если обе первые попытки отклонены; уменьшение с накоплением относится к уже
возникшему обязательству хеджирования.

## Переход между движками

Общий интерфейс `TradeEngine` в runner-е, два адаптера и выбор v1/v2 флагом конфига
остаются отдельным этапом перед переводом первой живой стратегии. В этом PR общие
адаптеры подключены только к тестовому харнессу; переключения рабочего runner-а
одной правкой конфига пока нет. Отдельный PR для этой прослойки должен сохранить
одинаковую обработку событий, учёт позиции и возможность вернуться к v1 без
переписывания подключения стратегии.

## Подключение

```go
limit, _ := budget.New(100, 10)
broker, _ := finambroker.NewGateway(finamClient, limit, "[pair-a]")

engine, err := execengine2.NewEngine(execengine2.Config{
    LegA: "LEGA@RTSX",
    LegB: "LEGB@RTSX",
    Lots: 1,
    Mode: execengine2.ModeTwoLimits,
}, execengine2.Setup{
    Broker:   broker,
    Limit:    limit,
    Strategy: strategy,
})
```

Если лимит общий для нескольких движков, им передаётся один и тот же
`*budget.Atomic`.
